# 第 1 章 — Runtime Live Machine Pro：一种理念

---

*作者手记*

十五年的开麦经历，会在亲历者身上留下清晰的印记。我做过播客，主持过谈话节目，独力撑起过一家网络电台，而在这段时间的大半里，一切都是我一个人在扛：播出单、音乐、访谈、音量、节奏。我知道那种滋味——直播中忽然发现歌快放完了，而你脑子里要说的话还没组织好。我也知道那是什么感觉：一只手压推子、另一只手去找正确的片段，而那第三只手——你本来没有的那只——本该替你接住话头。

Runtime Live Machine Pro 正诞生于那份挫败，以及一个朴素的信念：音频导播不该是一份独立的工作，它应当是透明的。那位深夜独自主持谈话节目的主播、播客作者、内容创作者——身边没有音响师做帮手——应当能够专注于他最擅长的事：说话、思考、与听众建立联系。其余的交给软件。

我把一位优秀的声音导播会自动执行的规则装进了 RLMP：音频事件之间的层级、你一开口就触发的 ducking、在恰当时机停下又续上的音乐。这些复杂的规则，都藏在一个只要求一个动作的界面之下：在恰当的时机点对正确的片段。

这款软件首先是为经营中小型谈话电台的人、为怀有专业野心的播客制作者、为身边没有技术团队却要推出直播流的人而设计的。但它的本性并不排他：在更成体系的环境中工作的人，也会找到契合自身需求的工具。目标只有一个：让主播摆脱对支援人手的依赖——那些人手并非总在场，也并非总是必需。

---

每一件工具都源自一个回应。Runtime Live Machine Pro 回应的是一个明确的问题：现场音频导播（电台、播客、活动、剧场）是一项表演，而非自动化。它需要瞬时的掌控、稳定的心态，以及一款不会在错误时刻背叛你的软件。

你电脑上装的这款软件，既不是全天候的音乐排期系统，也不是用于后期制作的 DAW，更不是一个带队列的简易播放器。它是另一种东西：一台**实时导播机器**，围绕着这样一个理念构建——每一场节目都是独一无二、不可复制的一次演出，值得一个专属的容器，以及对每一次转场的精细掌控。

---

## 1.1 为谁而造

Runtime Live Machine Pro 面向两类用户，尽管所处环境不同，他们却共享同一个根本需求。

**广播专业人士**——商业电台的导播、音频或视频直播的音响师、独自掌控自家节目的主播——会在 RLMP 中找到一套堪比高端专业设备的系统，同时具备那些系统往往为复杂度而牺牲掉的操作敏捷性。

**内容创作者**——独立播客作者、网络电台主持人、现场活动的组织者——会找到一款无需数年技术培训就能驾驭的工具，而它在结果的质量上绝不妥协。

两类用户都会得到一个对按键即时响应的界面、一个稳定的音频引擎，以及一套不会遗忘的保存系统。

---

## 1.2 「Single Show」理念

Runtime Live Machine Pro 的立身之本是**隔离的项目**。你制作的每一场节目——一期播客、一场电台直播、一次剧场演出——都存活在一个独立的 `.lmp` 文件里，其中包含一切：片段的布局、音量、MIDI 映射、cue 点、导播笔记。当你加载那个文件时，会原封不动地找回你离开时的那场节目。

这种做法带来实实在在的好处。你不必每次在节目之间切换时都重新配置软件。你可以把一个项目带到任意一台电脑上——借助 Export Package 功能——并确信它能正常运行。你可以归档往期节目，几个月后重新打开，不会有任何意外。

`.lmp` 文件并不包含物理的音频文件：它记录的是文件在磁盘上的路径。若需在多台电脑之间迁移，**Export Package** 功能会把所有必需内容物理地复制到一个自包含的文件夹中。

---

## 1.3 Main-Side-Heavy 架构

理解内部架构对使用软件并非必需，但它有助于理解为什么其他播放器常见的某些问题在这里不会出现。

Runtime Live Machine Pro 构建于 **Electron** 之上，这一平台将主进程（*Main Process*，运行于 Node.js）与界面渲染进程（*Renderer Process*）清晰地分开。这种分离在此被有意加以利用。

所有繁重的操作——通过 FFmpeg 解码音频、从磁盘读取文件、分析波形、管理备份——都交由 Main Process 处理。Renderer 只负责界面：显示片段、驱动 VU meter 的动画、响应点击。结果是：即使在密集操作期间，界面依旧流畅，而音频引擎也不会与屏幕上的像素争抢资源。

自定义的 `media://` 协议确保音频文件绝不会被整体载入内存 RAM：它们以流的方式直接从磁盘传送到播放器。你可以处理时长达数小时的未压缩 WAV 文件，而应用的内存占用不会有可察觉的变化。

## 1.4 导播网格：一套可视化的语法

RLMP 的操作界面被组织成若干竖直的列，每一列都有一个明确的语义角色。在启动软件之前，就值得先记住这套语法。

主网格中可见**六列**。第七个操作面——**pad FX**，即效果的 *jingle machine*——存活于网格之外，位于一个专属面板中，将在第 7 章描述。

| 列 | 颜色 | 功能 |
|---|---|---|
| **Show Assets** | 绿色 | 节目的片头、垫乐、结构性的背景铺底 |
| **Jingle** | 琥珀色 | 反复出现的标识性 jingle 与 stacco |
| **Promo** | 青色 | 预告、自我宣传、排期播出的通告 |
| **本期歌曲** | 红色 | 音乐播放列表 |
| **人声 / 预录** | 橙色 | 访谈、语音、口播段落 |
| **Pre-Show** | 紫色 | 直播前的候播音乐，附带 jingle 与 promo 的轮播 |

前三列（Show Assets、Jingle 与 Promo）在音频本质上是一致的：它们都是结构与服务性元素，被混音引擎同等对待。区分它们纯属组织上的考量：把片头、jingle 与 promo 分开，能让播出单在拥挤时依然清晰易读。

每一列都有各自不同的音频行为——混音中的优先级、互斥规则、淡变数值——这些将在第 6 章详述。目前只需知道：片段在网格中的位置并非装饰，它决定了软件在播出时如何对待这个片段。你用不到的列可以从视图中隐藏（设置 → 常规 → 导播布局），而不会丢失其中的片段。

## 1.5 当前版本与更新

本手册描述的是 Runtime Live Machine Pro 的 **1.11.5** 版本。启动时，软件会静默地检查是否有更新版本可用；若找到，会弹出一条更新提示——但绝不会在直播中弹出。更新系统在第 12 章描述。`.lmp` 项目文件与后续版本兼容：升级软件不会导致现有项目丢失，也无需手动迁移。
