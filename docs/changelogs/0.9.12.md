# Changelog v0.9.12

*Data: 2026-04-05*

## 🔧 Pulizia Architetturale — Rimozione Codice Morto

### [GR8] Eliminazione file preload duplicato e inutilizzato

**File eliminato**: `src/main/preload.ts`

**Problema**:
Il progetto conteneva due file preload distinti:

- `src/preload/index.ts` — il preload **reale**, con l'espansione completa
  di tutte le API Electron verso il renderer: `saveProject`, `loadProject`,
  `exportProject`, `getDevices`, `onExportProgress`, ecc.
- `src/main/preload.ts` — un preload **fantasma** che espone solo oggetti vuoti:
  `contextBridge.exposeInMainWorld('electron', {})` e
  `contextBridge.exposeInMainWorld('api', {})`.

La configurazione `webPreferences.preload` in `src/main/index.ts` punta correttamente
a `../preload/index.js`, quindi `src/main/preload.ts` **non veniva mai caricato**.
Era il file template generato automaticamente dallo scaffold Electron-Vite che non
era stato rimosso.

**Rischio**:
Se per errore il path del preload fosse stato corretto verso questo file (es. durante
un refactoring del main), l'applicazione avrebbe perso silenziosamente tutte le API
IPC, con errori criptici "window.electron.saveProject is not a function".

**Soluzione**: File eliminato definitivamente.

---

### [GR1] Eliminazione DuckingManager: sistema di ducking duplicato mai usato

**File eliminato**: `src/renderer/src/engine/DuckingManager.ts`

**Problema**:
Esisteva una classe `DuckingManager` (44 righe) dedicata al controllo del ducking
audio (abbassamento della musica quando entra la voce). La classe implementava
un pattern Singleton con `getInstance()` e un metodo `updateDucking(activePrioritySources)`.

Tuttavia, l'intera logica di ducking era già stata **reimplementata completamente**
nella funzione `evaluateMix()` di `useAudioStore.ts`, che è quella effettivamente
utilizzata dal motore audio. `evaluateMix` gestisce ducking, stacco, soppressione
e ripristino dei volumi in modo centralizzato e reattivo allo stato Zustand.

Cosa confermava che `DuckingManager` fosse codice morto:
- Nessun `import DuckingManager` trovato in tutto il codebase (`src/renderer/`)
- Nessuna chiamata a `DuckingManager.getInstance()` al di fuori del file stesso
- La logica di `updateDucking` operava direttamente sull'`AudioContextManager`
  tramite il bus master, sovrapponendosi all'approccio per-clip di `evaluateMix`

**Rischio del codice morto**:
Un futuro developer che leggesse il file avrebbe potuto:
- Credere che il ducking fosse gestito lì e fare modifiche al modulo sbagliato
- Tentare di richiamare `DuckingManager.getInstance().updateDucking()` da un
  nuovo trigger, ottenendo comportamenti imprevedibili in parallelo a `evaluateMix`

**Soluzione**: File eliminato definitivamente. La logica di ducking è interamente
e correttamente gestita da `evaluateMix` in `useAudioStore.ts`.
