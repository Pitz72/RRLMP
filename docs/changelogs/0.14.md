## Feature 1 — Import Playlist M3U → colonna PRE-SHOW

Nuovo pulsante `ListMusic` nella toolbar (dopo "Carica Progetto") che importa una playlist `.m3u` / `.m3u8` direttamente nella colonna PRE-SHOW.

### Flusso

1. Click sul pulsante "Importa Playlist M3U → PRE-SHOW"
2. Dialog di selezione file filtrato per `.m3u` / `.m3u8`
3. Il main process legge e parsa il file:
   - Salta righe `#EXTM3U`, `#EXTINF:...` e righe vuote
   - Risolve path relativi rispetto alla cartella dell'M3U
   - Filtra path non esistenti su disco e file non audio
4. Le tracce valide vengono aggiunte sequenzialmente alla colonna PRE-SHOW con:
   - `nextAction: 'play_next'` (default PRE-SHOW)
   - Auto-silence detection IPC in background su ogni traccia
5. Toast di conferma: `"M3U importata — N tracce aggiunte a PRE-SHOW"`

### Compatibilità

| Sistema | Supporto |
|---------|----------|
| M3U semplice (path assoluti) | ✅ |
| M3U con path relativi | ✅ (risolti rispetto alla cartella del file) |
| M3U8 (UTF-8) | ✅ |
| Extended M3U (`#EXTINF`) | ✅ (le direttive vengono saltate, solo i path vengono letti) |
| File audio supportati | mp3, wav, ogg, m4a, aac, flac, opus, wma |

# Changelog v0.14.10 (2026-04-09)

## Fix Release: Rilevamento Silenzio e Transizioni PRE-SHOW

Questa release risolve tre bug critici che rendevano non funzionanti il rilevamento automatico del silenzio al drop e le transizioni Crossfade/Segue nella colonna PRE-SHOW.

---

## Bug 1 — Crash OOM residuo in `loadClip` (critico)

### Problema
Il fix OOM di v0.14.6 aveva corretto il pulsante "Auto-Trim" in `ClipSettingsModal`, ma aveva lasciato intatta una seconda implementazione renderer-side del rilevamento silenzio all'interno di `loadClip()` in `useAudioStore.ts`. Questo codice:

```ts
const response = await fetch(fetchPath);
const arrayBuffer = await response.arrayBuffer();
const ctx = AudioContextManager.getInstance().getContext();
const audioBuffer = await ctx.decodeAudioData(arrayBuffer); // OOM su file grandi
```

Veniva eseguito per **ogni clip PRE-SHOW senza trim impostato**, causando il medesimo rischio di crash OOM per file audio di grandi dimensioni.

### Fix
Rimosso completamente il blocco renderer-side da `loadClip`. Il rilevamento del silenzio per PRE-SHOW avviene esclusivamente via IPC in `handleNativeDrop` (MainGrid.tsx), dove già funzionava correttamente tramite FFmpeg nel main process.

---

## Bug 2 — Transizioni Crossfade/Segue non funzionanti (critico)

### Problema
La funzione `applyTransitionAndPlayNext()` — che contiene tutta la logica corretta per crossfade (fade-out + fade-in incrociato), segue (fade-out rapido + FADE OUT badge), e gapless — era stata scritta ma **non veniva mai chiamata**.

I callback `onPreEnd` e `onOutroReached` chiamavano direttamente `get().playClip(nextClip)` senza eseguire alcun fade-out sulla clip corrente.

In più, `onPreEnd` scattava solo **50ms prima della fine** della clip (con `fadeOut=0` su PRE-SHOW), rendendo impossibile qualsiasi overlap significativo.

Infine, `applyTransitionAndPlayNext` leggeva `preshowTransitionType` (default: `'gapless'`, mai aggiornato dall'UI) invece di `defaultPreshowTransition` (il campo effettivamente modificabile dall'utente nelle impostazioni).

### Fix

**1. Collegamento di `applyTransitionAndPlayNext`:**
```ts
// Prima (onPreEnd)
get().playClip(nextClip); // nessun fade-out

// Dopo
applyTransitionAndPlayNext(clipId); // fade-out + fade-in coordinati
```

**2. Timing dinamico del fadeOut pre-play:**
Prima di `player.play()`, per le clip PRE-SHOW con `play_next` e senza Outro Marker, viene impostato `fadeOut` dinamicamente in base al tipo di transizione globale:
```ts
if (transType === 'crossfade') player.updateSettings({ ...freshClip, fadeOut: crossfadeDuration });
else if (transType === 'segue')  player.updateSettings({ ...freshClip, fadeOut: segueDuration });
```
Questo garantisce che `onPreEnd` scatti `crossfadeDuration` ms (es. 2000ms) o `segueDuration` ms (es. 800ms) prima della fine — non 50ms.

**3. Unificazione del campo transizione:**
`applyTransitionAndPlayNext` ora legge `defaultPreshowTransition` (il campo UI) invece di `preshowTransitionType`.

---

## Bug 3 — Nessun feedback visivo durante l'analisi del silenzio

### Problema
Il badge "TRIM…" sulla singola ClipCard era l'unico indicatore visivo durante il rilevamento del silenzio IPC. Con più file droppati contemporaneamente, non era chiaro quante analisi fossero in corso.

### Fix
Aggiunto banner a livello di colonna PRE-SHOW con contatore dei file in analisi:

```
● Rilevamento silenzio… 3 file in analisi
```

Il banner appare automaticamente al drop e scompare quando tutte le analisi sono complete. Usa `preshowAnalyzingCount` (stato locale in MainGrid) incrementato/decrementato tramite `.finally()` sulla Promise IPC.

---

## 🔴→⬛ Badge "FADE OUT" sulla ClipCard durante transizioni

### Problema risolto

Quando una transizione Crossfade o Segue era in corso, la clip uscente continuava a sembrare normale sulla ClipCard — nessun indicatore visivo che il fade stesse avvenendo. L'operatore non aveva feedback visivo immediato sullo stato della transizione.

### Implementazione

**Refactoring `transitioningClips`**: il `Set<string>` module-level (non reattivo) è stato sostituito con `fadingClipIds: string[]` nello stato Zustand. Questo permette ai componenti React di sottoscriversi e reagire.

**Badge ClipCard**: quando `fadingClipIds.includes(clip.id)` è true, la card mostra un badge viola pulsante `● FADE OUT`. Scompare automaticamente quando il fade termina e `stopClip` viene chiamato.

```tsx
{isFading && (
    <span className="... bg-violet-500/20 text-violet-300 border border-violet-500/40 ... animate-pulse">
        <span className="w-2 h-2 rounded-full bg-violet-400" />
        FADE OUT
    </span>
)}
```

**Ciclo di vita badge**:
1. Transizione avviata (`effectiveType === 'crossfade' | 'segue'`) → `fadingClipIds` include il clipId
2. Fade-out in corso → badge violet pulsante visibile
3. `setTimeout` scade (durata fade + 200ms) → `stopClip` + rimozione da `fadingClipIds`
4. Badge scompare

**Emergency Stop**: `stopAll()` ora resetta anche `fadingClipIds: []`.

# Changelog v0.14.8 (2026-04-07)

## Feature Release: Waveform Zoom + Durate Transizioni Separate

---

## 🔍 Zoom Orizzontale Waveform

### Problema risolto

Il WaveformEditor mostrava sempre la traccia intera compressa in un'unica vista. Su file lunghi (3-5 minuti), i marker di trim nelle prime o ultime centinaia di millisecondi erano impossibili da posizionare con precisione.

### Implementazione

**6 livelli di zoom**: 1x · 2x · 3x · 4x · 6x · 8x, controllati da pulsanti `−` / `+` nella legenda del waveform.

**Architettura scroll**:
- Container esterno (`scrollContainerRef`): `overflow-x: auto`, larghezza fissa
- Container interno (`containerRef`): `width: zoom * 100%`, è lo spazio di coordinate
- Tutti i calcoli di posizione (drag, seek, marker) usano `containerRef.getBoundingClientRect()` che restituisce già la posizione corretta compensando lo scroll — zero modifiche alla logica drag

**Ruler adattivo**: il numero di tick del righello scala con lo zoom:
- 1x → 3 tick (0, metà, fine)
- 2x → 5 tick
- 3-4x → 9 tick
- 6-8x → 13 tick

### File modificati

| File | Modifica |
|------|----------|
| `src/renderer/src/components/ui/WaveformEditor.tsx` | `scrollContainerRef`, `zoom` state, `zoomIn`/`zoomOut`, wrapper scrollabile, ruler adattivo, pulsanti `ZoomIn`/`ZoomOut` da lucide-react |

---

## 🎚️ Durate Separate Segue / Crossfade

### Problema risolto

Segue e Crossfade condividevano `crossfadeDuration`. In broadcast Segue ha semantica diversa: la clip entrante deve partire subito a volume pieno mentre la precedente sfuma rapidamente in background. Usare la stessa durata del Crossfade (2000ms) per il Segue risultava in un fade-out eccessivamente lento.

### Implementazione

**Nuovo campo `segueDuration`** (default: 800ms) nel settings store, separato da `crossfadeDuration` (default: 2000ms).

Comportamento:
- **Crossfade**: fade-out clip uscente su `crossfadeDuration` + fade-in clip entrante su `crossfadeDuration`
- **Segue**: fade-out clip uscente su `segueDuration` (più breve) + clip entrante parte immediatamente a pieno volume

**UI**: due slider distinti nel `GeneralSettingsModal` — Crossfade (200ms–6000ms, verde) e Segue Fade-Out (100ms–3000ms, arancione).

### File modificati

| File | Modifica |
|------|----------|
| `src/renderer/src/store/useSettingsStore.ts` | Aggiunto `segueDuration: number` (default 800ms), `setSegueDuration` setter |
| `src/renderer/src/store/useAudioStore.ts` | Transizione Segue usa `segueDuration` invece di `crossfadeDuration` |
| `src/renderer/src/components/modals/GeneralSettingsModal.tsx` | Due slider separati: Crossfade Duration + Segue Fade-Out Duration |

Sostituisce tutti i `alert()` e `confirm()` nativi del browser con un sistema di notifiche non-bloccante e un dialog di conferma inline. Elimina il principale problema di professionalità broadcast: l'interfaccia che si congela durante la messa in onda.

---

## 🔔 Toast Notification System

### Problema risolto

Tutti i messaggi di errore, avviso e conferma usavano `alert()` / `confirm()` nativi del browser, che:
- **Bloccano completamente l'interfaccia** — inaccettabile durante una trasmissione live
- Non hanno stile coerente con l'app
- Non possono essere accodati o ignorati dall'operatore
- Non sono disponibili in contesto Electron senza attivazione manuale

### Architettura

**`useToastStore`** (Zustand) — store globale toast:
- `addToast(message, type, duration?)` — aggiunge un toast con auto-dismiss
- `removeToast(id)` — rimozione manuale via pulsante X
- `toast()` — helper callable da qualsiasi file senza hook React
- Tipi: `success` (4s), `error` (6s), `warning` (4s), `info` (4s)
- Stack max 5 toast visibili contemporaneamente

**`useConfirmStore`** (Zustand) — dialog di conferma promise-based:
- `confirm(message, confirmLabel?, cancelLabel?)` → `Promise<boolean>`
- Non-bloccante: usa `await` nei gestori async invece di bloccare il thread
- Helper `confirm()` callable da qualsiasi file

**`ToastContainer`** — UI toast:
- Posizione fixed bottom-right, z-index 200
- Icona per tipo (✓ success, ✕ error, ⚠ warning, ℹ info)
- Barra di progresso CSS animata che indica il tempo rimanente
- Pulsante X per chiusura manuale
- Colori: emerald (success), red (error), amber (warning), cyan (info)

**`ConfirmDialog`** — UI conferma:
- Modal overlay con z-index 300 (sopra i toast)
- Icona ⚠ amber, messaggio, pulsanti Conferma/Annulla personalizzabili
- `autoFocus` sul pulsante Conferma per workflow tastiera rapido
- Stile coerente con il resto dell'app (zinc/dark)

## ⚡ Feedback Visivo Auto-Silence (§2.1)

### Problema risolto

Quando una clip veniva droppata nella colonna PRE-SHOW, `detectSilence()` girava in background via IPC FFmpeg per 1-5 secondi senza alcun feedback visivo. L'utente non sapeva se il trim fosse in corso o già completato.

### Soluzione

**Flag runtime `isAnalyzing?: boolean`** su `AudioClip` (non persistito nel `.lmp`).

Ciclo di vita:
1. Drop nella colonna PRE-SHOW → `updateClip(..., { isAnalyzing: true })`
2. `detectSilence()` gira in background
3. Risultato ricevuto (successo o errore) → `updateClip(..., { isAnalyzing: false })`

**Badge ClipCard:** badge ambra pulsante `⚡ TRIM…` con dot `animate-ping` finché `isAnalyzing` è true.

## 🔴 UP NEXT Badge Dinamico (§4.3)

### Comportamento

Il badge **▶ UP NEXT** appare sulla clip che verrà riprodotta **automaticamente** come prossima, in base allo stato corrente di playback — non sul valore statico di `nextAction`.

**Condizioni di attivazione:**
1. Una clip nella stessa colonna è attualmente in riproduzione
2. La clip in play ha `nextAction === 'play_next'`
3. Questa clip è immediatamente successiva nella lista

**Differenza dal badge NEXT esistente:**
| Badge | Quando appare | Significato |
|-------|--------------|-------------|
| `NEXT` (emerald) | Sempre, se `nextAction = play_next` | Proprietà statica — "questa clip ha l'autoplay" |
| `▶ UP NEXT` (violet, pulsante) | Dinamicamente, durante la riproduzione | Stato live — "questa è la prossima clip IN CODA ORA" |

I due badge sono mutualmente esclusivi: quando `isNextUp` è true, il badge NEXT statico viene nascosto e sostituito da UP NEXT.

### Visual Design

- Colore: **violet** (`bg-violet-500`)
- Glow effect: `shadow-[0_0_6px_rgba(139,92,246,0.7)]`
- Animazione: `animate-pulse` per indicare stato live
- Testo: `▶ UP NEXT`

### Implementazione

Il calcolo di `isNextUp` è completamente reattivo: è un `useMemo` che dipende da `useAudioStore.activeClips` e `useProjectStore.columns`. Si aggiorna automaticamente a ogni cambio di playback.

```typescript
// In ClipCard
const isNextUp = React.useMemo(() => {
    const col = columns.find(c => c.clips.some(cl => cl.id === clip.id));
    if (!col) return false;
    const clipIdx = col.clips.findIndex(c => c.id === clip.id);
    if (clipIdx <= 0) return false;
    const prevClip = col.clips[clipIdx - 1];
    return prevClip.nextAction === 'play_next' && !!activeClips[prevClip.id];
}, [columns, activeClips, clip.id]);
```

## 🚨 Feature Release: Emergency Stop Globale (Escape → stopAll)

Questa release implementa il punto **§4.2** della VISION.md ("Hotkey Globale Emergency Stop", priorità 🔴 CRITICO). La pressione del tasto `Escape` ferma immediatamente **tutte le clip in riproduzione** tramite `globalShortcut` Electron, garantendo il funzionamento anche quando il focus è su un elemento interno all'app (modali, input, canvas).

---

## 🔍 Funzionamento

### Flusso Emergency Stop

1. L'utente preme `Escape` (in qualsiasi momento, app in primo piano)
2. Il main process intercetta la scorciatoia via `globalShortcut`
3. Viene inviato l'evento IPC `emergency-stop` a tutte le finestre aperte
4. Il preload bridge trasporta l'evento al renderer via `onEmergencyStop`
5. Il renderer chiama `useAudioStore.getState().stopAll()`
6. Tutti i player vengono fermati e il mix viene azzerato istantaneamente

### Caratteristiche

- **Globale a livello di app**: funziona anche con un input testuale, modale o canvas in focus
- **Basato su OS-level globalShortcut**: la registrazione avviene nel main process Electron
- **Cleanup corretto**: `globalShortcut.unregisterAll()` su `app.on('will-quit')` — nessun leak
- **Idempotente**: se non ci sono clip attive, la chiamata a `stopAll()` è no-op

### Nota su Comportamento Globale OS

`globalShortcut` in Electron intercetta il tasto a livello di OS quando la finestra è in primo piano. Per design, `Escape` viene riservato come Emergency Stop esclusivo dell'app. In modalità broadcast professionale questo è il comportamento corretto: il tasto di emergenza deve essere affidabile e immediato.

Questa release implementa il punto **§4.1** della VISION.md ("LMP Integrity Check", priorità 🔴 CRITICO). All'apertura di un progetto `.lmp`, il sistema verifica automaticamente l'esistenza su disco di tutti i file audio referenziati. Le clip con file mancanti vengono marcate visivamente e bloccate in playback senza interrompere il caricamento del progetto.

---

## 🔍 Funzionamento

### Flusso di caricamento con Integrity Check

1. L'utente apre un file `.lmp` tramite il pulsante Carica (o da Welcome Screen)
2. `loadProject()` carica le colonne nello store, resettando `isMissing: false` su tutte le clip
3. Subito dopo, `runIntegrityCheck()` viene chiamato in modo asincrono
4. Il renderer invia tutti i path via IPC al main process (`check-files-exist`)
5. Il main verifica `fs.existsSync()` per ogni path e ritorna l'array dei mancanti
6. Lo store aggiorna `isMissing: true` sulle clip corrispondenti
7. Le ClipCard si re-renderizzano: clip mancanti mostrano lo stato di errore visivo

### Caratteristiche

- **Non-blocking**: il caricamento del progetto non viene bloccato dai file mancanti. Le clip presenti funzionano normalmente
- **Runtime only**: `isMissing` è un flag di stato volatile, non viene serializzato nel `.lmp`
- **Sicuro su reset**: `loadProject()` resetta `isMissing: false` su tutte le clip prima del check

    const state = useProjectStore.getState();
    const allClips = state.columns.flatMap(col => col.clips);
    const paths = allClips.map(c => c.path).filter(Boolean);

## 🖱️ Drag & Drop Interattivo (WaveformEditor v2)

### Problema originale
Dalla v0.10.0, il changelog prometteva "maniglie trascinabili" per Trim Start/End, Intro e Outro. L'implementazione originale basata su Wavesurfer.js non fu mai completata, e con la migrazione alla strategia Main-Side-Heavy (v0.10.7), i marker erano rimasti accessibili solo tramite pulsanti click-based ("Set Trim Start", "Set Intro", ecc.).

### Implementazione

#### 4 Handle Drag & Drop Visivi
- **Trim Start** (rosso, sinistra): handle a barra verticale sul bordo destro della zona di taglio sinistra
- **Trim End** (rosso, destra): handle sul bordo sinistro della zona di taglio destra
- **Intro** (cyan, linea verticale): handle direttamente sulla linea dell'intro marker — visibile solo se introMarker > 0
- **Outro** (arancione, linea verticale): handle sulla linea dell'outro marker — visibile solo se outroMarker > 0

#### Meccanica Drag
- `onMouseDown` sull'handle → attiva lo stato `dragging` (tipo marker)
- `document.addEventListener('mousemove')` e `'mouseup'` per tracking globale — il drag continua anche uscendo dal container
- Conversione `clientX` → secondi: `(clientX - containerRect.left) / containerRect.width * duration`
- `onChange(updates)` chiamato live durante il drag → aggiornamento visivo in tempo reale
- `stopPropagation()` nell'handle MouseDown → non triggera il seek per click

#### Pattern Anti-Stale Closure (Ref Sync)
I valori `trimStart`, `trimEnd`, `duration` e `onChange` vengono mantenuti in `useRef` e aggiornati ad ogni render. Il `useEffect` del drag dipende **solo da `dragging`**, evitando la registrazione/deregistrazione dei listener ad ogni cambio di posizione durante il drag.

```typescript
const onChangeRef   = useRef(onChange);
const trimStartRef  = useRef(trimStart);
const trimEndRef    = useRef(trimEnd);
const durationRef   = useRef(0);
// Aggiornati nel corpo del componente (inline, senza useEffect) — safe in React
onChangeRef.current  = onChange;
trimStartRef.current = trimStart;
...
```

#### Constraint Logic
- **Trim Start** non può superare `duration - trimEnd - 0.05s` (almeno 50ms di clip)
- **Trim End** non può essere tale da far iniziare prima del Trim Start

# Changelog v0.14.0 (2026-04-06)

## 🔧 BUGFIX CRITICO: Smart Trim — OOM Crash su File Grandi

### Problema
Cliccare il pulsante **Auto-Trim (Wand)** nelle impostazioni clip causava un crash irreversibile del renderer (schermo bianco, app da terminare forzatamente).

### Causa Radice
La funzione `detectSilence()` eseguiva l'intera analisi audio **dentro il renderer Chromium**:
1. `response.arrayBuffer()` caricava l'intero file audio in RAM come buffer binario
2. `audioCtx.decodeAudioData()` lo decodificava in PCM Float32, raddoppiando l'occupazione di memoria

Per file WAV non compressi (tipici in broadcast), questo significava **200–600MB** allocati nel renderer in pochi millisecondi → Out-Of-Memory → crash del processo V8 → schermo bianco.

### Fix (Main-Side-Heavy Architecture)
La logica di rilevamento silenzio è stata spostata completamente nel **main process (Node.js)** seguendo l'architettura già consolidata per la generazione della waveform:

- **`AudioProcessor.ts`** — Nuovo metodo statico `detectSilence()` che usa FFmpeg con il filtro `silencedetect=noise=-40dB:d=0.1`. FFmpeg analizza il file come subprocess e ritorna solo i timestamp (`silence_start` / `silence_end`) via stderr. Zero RAM aggiuntiva nel renderer.
- **`main/index.ts`** — Nuovo IPC handler `detect-silence`.
- **`preload/index.ts`** — Esposto `detectSilence()` via contextBridge.
- **`types/index.ts`** — Aggiunto tipo `detectSilence` all'interfaccia `Window.electron`.
- **`ClipSettingsModal.tsx`** — `detectSilence()` ora chiama `window.electron.detectSilence(clip.path)` e applica i valori restituiti. Nessun `fetch`, nessun `AudioContext`, nessun buffer in-renderer.

### Fix aggiuntivo
- **`AudioProcessor.ts`** — Aggiunto handler `.on('error')` mancante su `ffStream` in `generateWaveformData()`. In assenza di questo handler, un errore sul pipe stream avrebbe emesso un evento `error` non gestito, potenzialmente crashing il main process.

### Comportamento post-fix
| Condizione | Risultato |
|---|---|
| Silenzio iniziale e/o finale rilevato | Imposta trimStart / trimEnd, mostra alert |
| Nessun silenzio rilevato | Alert informativo, nessun trim applicato |
| File non trovato | Messaggio di errore |
| Intero file silenzioso | Messaggio di errore specifico |
