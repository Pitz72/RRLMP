## 1 — Fix Critico: Base Musicale Abbassa il Volume all'Avvio

### Problema

Quando veniva avviata una clip musicale (base) mentre lo speaker parlava o un'altra clip era già in riproduzione, la base partiva a volume pieno (1.0) e poi si abbassava progressivamente verso il volume duckato nel giro di `duckingDuration` ms (es. 500ms). Questo causava un calo di volume percepibile che non avrebbe dovuto esserci.

### Causa

In `useAudioStore.ts`, la funzione `playClip()` chiama:
1. `player.play()` — imposta il gain a `clip.volume` (1.0)  
2. `evaluateMix()` — ricalcola i volumi e chiama `player.fadeTo(targetVolume, duckingDuration)` con una durata smooth

Per la clip appena avviata, questo creava una transizione graduale da 1.0 → volume duckato, visibile e udibile.

### Fix — doppia correzione

**A) `StreamPlayer.fadeTo()` — bug con `duration=0`**

`linearRampToValueAtTime(v, now + 0)` può causare glitch audio nella Web Audio API. Aggiunto branch esplicito:

```typescript
if (duration <= 0) {
    this.volumeGainNode.gain.setValueAtTime(volume, now);
} else {
    this.volumeGainNode.gain.setValueAtTime(this.volumeGainNode.gain.value, now);
    this.volumeGainNode.gain.linearRampToValueAtTime(volume, now + (duration / 1000));
}
```

**B) `evaluateMix()` — istantaneo per la clip appena avviata**

La firma è cambiata da `evaluateMix(activeClips)` a `evaluateMix(activeClips, newClipId?)`. Quando `newClipId` corrisponde alla clip in elaborazione, la durata del fade è 0 (istantaneo):

```typescript
const applyDuration = (newClipId && clip.id === newClipId) ? 0 : duckingDuration;
player.fadeTo(targetVolume, applyDuration);
```

La chiamata in `playClip()` è aggiornata: `evaluateMix(newState.activeClips, freshClip.id)`.

**Risultato**: la base parte direttamente al volume corretto, senza rampa percepibile.

**File modificati**: `src/renderer/src/engine/StreamPlayer.ts`, `src/renderer/src/store/useAudioStore.ts`

## 2 — Transizioni Crossfade/Segue/Gapless estese a Music e Assets

### Problema

Le transizioni automatiche (`play_next` con crossfade/segue/gapless) erano attive solo per le clip di tipo `preshow`. Le canzoni dell'episodio (Music) e gli Assets con `nextAction: 'play_next'` non beneficiavano del fade-out dinamico necessario per far scattare `onPreEnd` al momento giusto.

### Fix

Rimosso il guard `freshClip.type === 'preshow'` nella logica di `playClip()` in `useAudioStore.ts`:

```typescript
// Prima:
if (freshClip.type === 'preshow' && freshClip.nextAction === 'play_next' && ...) {
// Dopo:
if (freshClip.nextAction === 'play_next' && ...) {
```

Ora tutte le clip con `nextAction: 'play_next'` — indipendentemente dal tipo — ricevono il fade-out dinamico calibrato sulla transizione configurata (crossfade/segue/gapless).

### Fix collegato: ClipSettingsModal — pulsante Test→ per tutte le clip

In `ClipSettingsModal.tsx`, la funzione `hasNextClip` aveva un guard `if (clip.type !== 'preshow') return false` che impediva al pulsante "Test→" di apparire per canzoni e asset. Rimosso:

```typescript
const hasNextClip = useMemo(() => {
    // Rimosso: if (clip.type !== 'preshow') return false;
    const col = columns.find(c => c.clips.some(cl => cl.id === clip.id));
    ...
```

**File modificati**: `src/renderer/src/store/useAudioStore.ts`, `src/renderer/src/components/modals/ClipSettingsModal.tsx`

## 3 — Metadati ID3: Artista e Titolo sulle Clip Musicali

### Funzionalità

Le clip di tipo `music` ora mostrano **titolo e artista** estratti dai tag ID3/Vorbis del file audio.

### Architettura

**Tipo**: aggiunti `artist?: string` e `title?: string` a `AudioClip` in `types/index.ts` (persistiti nel `.lmp`).

**Estrazione**: in `loadClip()` (`useAudioStore.ts`), per le clip `music` senza metadati già presenti, viene chiamato `window.electron.getAudioMetadata(clip.path)` (IPC già esistente). I campi `common.artist` e `common.title` della risposta vengono salvati via `updateClip()`.

```typescript
if (clip.type === 'music' && !clip.artist && !clip.title) {
    const meta = await window.electron.getAudioMetadata(clip.path);
    if (meta.success && meta.data) {
        const tags = (meta.data as any).common || {};
        if (tags.artist) artist = tags.artist;
        if (tags.title) title = tags.title;
    }
}
```

Il fallback è non-fatale: se il tag non esiste o la chiamata fallisce, la clip mostra il filename come prima.

**Visualizzazione** (`ClipCard.tsx`):
- Il nome della clip mostra `clip.title` se disponibile, altrimenti `clip.name` (filename)
- Sotto il titolo appare `clip.artist` in un testo più piccolo (`text-[10px]`), nel colore della colonna al 60% verso bianco

```tsx
{clip.type === 'music' && clip.artist && (
    <span style={{ color: lightenHex(clip.color, 0.6) + 'bb' }}>
        {clip.artist}
    </span>
)}
```

**File modificati**: `src/renderer/src/types/index.ts`, `src/renderer/src/store/useAudioStore.ts`, `src/renderer/src/components/layout/ClipCard.tsx`

## 4 — Error Boundaries React

### Problema

Un errore di rendering in un componente figlio (es. `MainGrid`, una colonna, una `ClipCard`) poteva crashare l'intera applicazione, perdendo lo stato di sessione e richiedendo un riavvio manuale.

### Implementazione

Nuovo componente `ErrorBoundary` (`src/renderer/src/components/ui/ErrorBoundary.tsx`):
- Class component React (unico modo nativo per catturare errori di render)
- `getDerivedStateFromError` → mostra fallback UI
- `componentDidCatch` → log a console con identificatore zona
- Fallback UI: pannello rosso con messaggio errore + pulsante "Riprova" (reset dello stato)
- Prop `zone` per identificare la sezione (es. "MainGrid")
- Prop `fallback` opzionale per UI personalizzata

**Integrazione in `App.tsx`**:

```tsx
<ErrorBoundary zone="MainGrid">
    <MainGrid />
</ErrorBoundary>
```

**File creati**: `src/renderer/src/components/ui/ErrorBoundary.tsx`  
**File modificati**: `src/renderer/src/App.tsx`
