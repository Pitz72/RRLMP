## Feature — Simulatore MIDI (strumento di test)

### 1. `src/renderer/src/engine/MidiManager.ts` — `simulateMessage(data)`
Nuovo metodo pubblico che inietta una terzina raw `[command, note, velocity]` chiamando lo **stesso** `handleMidiMessage` usato dalle porte MIDI fisiche. Conseguenza: il messaggio simulato attraversa identicamente:
- il masking del nibble alto (`command & 0xF0`) per riconoscere Note On (`0x9n`) e CC (`0xBn`) su tutti i 16 canali;
- il filtro Note Off / Note On con velocity 0 (nessun trigger);
- il fan-out ai listener (`App.handleMidiMessage` → trigger clip, MIDI Learn, global binds).

I byte sono clampati a `[0,255]` prima dell'iniezione. Nessuna modifica al comportamento runtime esistente — è solo un nuovo punto d'ingresso di test verso codice già esistente.

### 2. `src/renderer/src/components/modals/MidiSimulatorModal.tsx` — nuova modale
Pannello di test aperto/chiuso con hotkey **Ctrl+Shift+M** (stesso pattern del Debug Overlay su Ctrl+Shift+D). Controlli:
- tipo messaggio: **Note On** / **Note Off** / **Control Change**;
- **Canale** 1-16 (mappato nel nibble basso del command byte: `status | (ch-1)`);
- **Nota** / CC# 0-127;
- **Velocity** / valore CC 0-127.

Mostra l'ultimo messaggio inviato in forma leggibile + raw. Etichettato esplicitamente come *strumento di test*. Coerente con il principio **stabilità > funzionalità**: non tocca il path audio in onda, è solo una superficie di test gated dietro hotkey.

### 3. `src/renderer/src/App.tsx` — wiring
- import `MidiSimulatorModal`;
- state locale `showMidiSim`;
- hotkey `Ctrl+Shift+M` nel `handleKeyDown` globale (accanto a Ctrl+Shift+D);
- render della modale.

## Bugfix — script `dev` (package.json)

Lo script:
```
... && set NODE_ENV=development && electron .
```
Su Windows `cmd`, `set NODE_ENV=development && ...` cattura **anche lo spazio** prima di `&&`, impostando `NODE_ENV` a `"development "` (con spazio finale). Il check in `src/main/index.ts` riga 199:
```ts
if (process.env.NODE_ENV === 'development') {
    mainWindow.loadURL('http://localhost:5173');   // server Vite live
} else {
    mainWindow.loadFile(join(__dirname, '../renderer/index.html'));  // build compilata
}
```
falliva → Electron caricava il **renderer compilato (stale)** invece del dev server. Risultato pratico: ogni modifica al codice renderer non appariva in `npm run dev` (si vedeva solo l'ultima `vite build`).

**Fix:** `set "NODE_ENV=development"` (forma quotata che elimina lo spazio finale). Una riga, solo `package.json`, nessun impatto sulla build di produzione.
