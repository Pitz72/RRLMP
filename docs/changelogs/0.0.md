# Log Dev 0.0.9fix1 (Sync & Crossfade Fix)
**Data**: 2026-01-04
**Autore**: Antigravity (Assistant)

## Fix Critico: Sincronizzazione Crossfade

Abbiamo risolto il problema per cui il comando **"Next Action: Play Next"** non si attivava correttamente o lasciava un buco di silenzio.

### Interventi Tecnici

1.  **Anticipo del Trigger (`onPreEnd`)**:
    *   È stato introdotto un nuovo evento nel `StreamPlayer` chiamato `onPreEnd`.
    *   Questo evento si attiva **prima** della fine del brano, esattamente quando inizia il **Fade Out** (o 50ms prima se non c'è fade).
    *   Questo permette allo store di ricevere il segnale "Sto finendo" mentre l'audio sta ancora suonando.

2.  **Logica di Store Aggiornata**:
    *   La `useAudioStore` ora ascolta `onPreEnd` invece del solo `onEnded` per lanciare la clip successiva.
    *   Risultato: La Clip B parte esattamente nell'istante in cui la Clip A inizia a sfumare (Crossfade Perfetto).

3.  **Pulizia**:
    *   Il listener `onEnded` rimane attivo solo per pulire le risorse della clip finita e rimuoverla dalla lista delle attive, evitando conflitti di doppio avvio.

### Stato Attuale
Questa build `0.0.9fix1` è ottimizzata per testare specificamente la fluidità del passaggio "Sigla -> Sottofondo" e l'affidabilità del comando Play Next.

-   **Release**: Quando tutte le clip prioritarie si fermano, la musica torna a volume pieno (fade fluido).

## Dettagli Tecnici
-   **AudioContextManager**: Ora espone i nodi dei bus.
-   **DuckingManager**: Singleton che osserva lo stato e modula il gain del Music Bus.
-   **StreamPlayer**: Aggiornato per supportare il routing dinamico (`setBus`).
-   **useAudioStore**: Gestisce la logica di routing al momento del `playClip` e notifica il DuckingManager.

# Log Dev 0.0.5fix13 (Legacy Audio Engine)
**Data**: 2026-01-04
**Autore**: Antigravity (Assistant)

## Problema
I tentativi di gestire lo streaming audio tramite protocollo personalizzato `media://` e Node.js Streams hanno introdotto glitch audio (loop iniziale) e instabilità nel seeking, dovuti alla complessità di replicare perfettamente le Range Requests HTTP/Video nativi.

## Soluzione (Backporting da _OLDAPP)
Analizzando la versione precedente funzionante (`_OLDAPP`), è emerso che la stabilità era, paradossalmente, dovuta a una configurazione di sicurezza meno restrittiva che permetteva l'uso diretto del protocollo `file://`.

### Modifiche Architetturali
1.  **Main Process (`main/index.ts`)**:
    -   Impostato `webSecurity: false` nelle `webPreferences`. Questo autorizza il Renderer a caricare risorse locali `file://` direttamente, aggirando il blocco CORS per i file locali.
    -   Rimossa (o resa obsoleta) la gestione complessa del protocollo `media://` per lo streaming.

2.  **Path Utils (`pathUtils.ts`)**:
    -   Aggiornata `toFileUrl` per restituire URI nel formato `file:///C:/path/to/file.mp3` invece del custom protocol.

3.  **Vantaggi**:
    -   **Nativo**: Il motore Chromium gestisce interamente il buffering, la cache e il decoding.
    -   **Zero Glitch**: Niente più "balbettii" iniziali dovuti a buffer Node.js mal dimensionati.
    -   **Seeking**: Supporto nativo immediato per saltare a qualsiasi punto della traccia.

## Note di Sicurezza
L'uso di `webSecurity: false` è generalmente sconsigliato in app che caricano contenuto remoto non fidato. Dato che RRLMP è un'applicazione offline/locale per uso broadcast su macchine controllate, questo trade-off è accettabile e necessario per garantire le performance audio richieste.

# Log Dev 0.0.5fix10 (Sanitizzazione Protocollo)
**Data**: 2026-01-03
**Autore**: Antigravity (Assistant)

## Problema: `net::ERR_UNEXPECTED` su Drive Esterno (J:)
Il test sul fix precedente ha mostrato un errore di fetch. Analizzando il log `media://J:/...` sembra che l'URL formato con doppio slash (`//`) causi un'interpretazione errata dell'authority (host) da parte del parser URL di Electron, trattando `J:` come host invece che parte del path, o causando problemi nel `decodeURIComponent` se non gestito perfettamente.

## Fix: Standardizzazione URI
1.  **Triple Slash**: Modificato `pathUtils` per generare `media:///${path}`. Questo è lo standard URI per "local file no host".
2.  **Robust Parsing**: Aggiornato il Main Process per usare una regex `^media:\/*` che rimuove qualsiasi variante di slash iniziale, garantendo che ciò che resta sia il path pulito.
3.  **Error Handling**: Aggiunto blocco `try/catch` nel protocol handler per intercettare malformazioni e loggare l'errore specifico invece di crashare silenziosamente o dare errori generici.

Build v0.0.5fix10 pronta in `builds/v0.0.5`.

# Log Dev 0.0.5fix8 (PROTOCOL REVOLUTION)
**Data**: 2026-01-03
**Autore**: Antigravity (Assistant)

## Analisi Forense Definitiva
Il crash persistente è dovuto alla gestione nativa dei puntatori ai file (File Object) in memoria da parte di Electron/Chromium durante il Drag & Drop. La garbage collection o la restrizione di sicurezza V8 dereferenziava il puntatore mentre l'audio engine cercava di bufferizzarlo, causando il crash del processo.

## Soluzione Implementata: Protocollo `media://`
Abbiamo cambiato radicalmente l'approccio.
1.  **Renderer Agnostico**: Il frontend non legge più nessun file. Non usa `FileReader`, né `Blob`, né `ArrayBuffer`. Riceve solo il path.
2.  **Protocollo Custom**: Abbiamo registrato `media://` nel processo Main.
    - Quando il frontend chiede `<audio src="media://C:/Music/song.mp3">`, la richiesta viene intercettata dal Main Process.
    - Il Main Process usa `net.fetch('file://...')` per servire lo stream in modo sicuro e nativo.
3.  **Path Retrieval**: Creato un bridge sicuro nel Preload (`getFilePath`) usando `webUtils.getPathForFile` per ottenere il percorso assoluto dal file droppato senza violare la sandbox.

## Risultato
- **Zero Memory Load**: Non carichiamo più 50MB di WAV in RAM JavaScript.
- **Zero Security Risk**: Il renderer non tocca il disco.
- **Stabilità Massima**: Lo streaming è gestito dal network stack di Chromium.

Build v0.0.5fix8 pronta in `builds/v0.0.5`.

# Log Dev 0.0.5fix5 (Nuclear Option)
**Data**: 2026-01-03
**Autore**: Antigravity (Assistant)

## Problema Risolto: Renderer Crash su Drag & Drop (Definitivo)
Nonostante i fix precedenti, il renderer process occasionalmente crashava o mostrava pagina bianca su drop in build di produzione.
**Causa Radice**: La gestione di `fetch` sui path locali in Electron è problematica e prona a errori di sicurezza e protocollo. Inoltre, il comportamento di default del browser di navigare al file droppato non era bloccato in modo sufficientemente aggressivo.

## "Nuclear Option" Applicata

1.  **Blocco Navigazione in `index.html`**: 
    - Inserito script nel `<head>` che intercetta `dragover` e `drop` a livello di documento, chiamando `preventDefault()` e `stopPropagation()`. Questo uccide qualsiasi tentativo di navigazione del browser prima che arrivi a React.

2.  **Lettura Diretta via `File` Object (Zero Fetch)**:
    - **BufferPlayer Riscritto**: Invece di `fetch(path)`, ora accetta direttamente l'oggetto `File` (Blob) quando disponibile (dal Drag & Drop).
    - Usa `file.arrayBuffer()` per leggere i dati direttamente dalla RAM. Questo bypassa completamente il network stack, i problemi CORS, i protocolli `file://` e i permessi del filesystem di Node. È il metodo più sicuro e veloce possibile.

3.  **Iniezione nello Store**:
    - `MainGrid` ora passa l'oggetto `File` nativo a `loadClip`.
    - `loadClip` usa questo oggetto come sorgente primaria se disponibile, usando il path solo come fallback per ricaricamenti futuri.

## Risultato
Build eseguita. Il Drag & Drop è ora gestito interamente in memoria per la lettura dati e bloccato a livello nativo per la navigazione. La stabilità dovrebbe essere massima.
