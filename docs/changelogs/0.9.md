### [M1] Dialog di chiusura con stringhe localizzate (i18n)

**File modificati**:
- `src/main/index.ts` — nuovo handler `show-close-dialog-i18n`
- `src/preload/index.ts` — esposto `showCloseDialogI18n` via contextBridge
- `src/renderer/src/App.tsx` — `handleCloseIntent` usa ora il dialog i18n

**Problema**:
Il dialog nativo "Modifiche non salvate?" mostrava sempre i tasti `Salva / Non Salvare / Annulla`
in italiano, indipendentemente dalla lingua selezionata nell'interfaccia.
I dialog nativi (Electron `dialog.showMessageBox`) vengono generati nel main process,
che non ha accesso al contesto i18next del renderer.

**Soluzione**:
Aggiunto un nuovo handler IPC `show-close-dialog-i18n` che accetta le label
come parametro invece di usare stringhe hardcoded:

```typescript
ipcMain.handle('show-close-dialog-i18n', async (_, labels) => {
    return dialog.showMessageBox(mainWindow, {
        buttons: [labels.btnSave, labels.btnDiscard, labels.btnCancel],
        title: labels.title,
        message: labels.message,
        ...
    });
});
```

Il renderer legge le traduzioni tramite `import('i18next')` dinamico
e le passa al main process. Se `showCloseDialogI18n` non è disponibile
(preload vecchio, ambiente test), cade in fallback sul vecchio handler legacy.

### [M2] Notifica visiva quando MIDI non è disponibile

**File modificati**:
- `src/renderer/src/engine/MidiManager.ts` — sistema `addStatusListener` + `MidiStatusCallback`
- `src/renderer/src/components/ui/GlobalControls.tsx` — badge MIDI sul pulsante

**Problema**:

**Soluzione**:

Nel badge del tasto MIDI in `GlobalControls`:
- ✅ **MIDI funzionante + controller connessi**: badge verde con il numero di input (es. `MIDI 2`)
- ✅ **MIDI funzionante ma 0 controller**: tasto normale senza badge
- ❌ **MIDI non supportato / errore**: tasto rosso con simbolo `✕` e tooltip "MIDI non disponibile"

### [M3] MIDI Learn: timeout automatico 15s + uscita con Escape

**File modificato**: `src/renderer/src/components/ui/GlobalControls.tsx`

**Problema**:
Premendo il tasto MIDI per avviare la modalità Learn, il software rimaneva in
attesa di un segnale MIDI indefinitamente. Se l'operatore dimenticava di premere
un tasto sul controller (o il controller non era connesso), la modalità Learn
restava attiva per tutta la sessione, alterando il comportamento di click e fader.

**Soluzione**:
Due meccanismi di uscita automatica:

1. **Timeout** — `useEffect` con `setInterval` decreta. Dopo 15 secondi di learn attivo
   senza input ricevuto, la modalità viene disattivata automaticamente e viene scritto
   un log nel debug overlay.

2. **Escape** — listener `keydown` che, se `key === 'Escape'` durante MIDI Learn,
   resetta immediatamente la modalità e annulla il `pendingBind`.

3. **Countdown visivo** — badge `{N}s` appare sull'angolo superiore del tasto MIDI
   durante il countdown, mostrando i secondi rimanenti prima del timeout automatico.

```
[MIDI 2]    ← badge verde: 2 controller connessi
[MIDI ✕]    ← rosso: MIDI non disponibile
[MIDI]      ← normale: pronto ma 0 controller
[ 12s ]     ← durante learn mode: countdown
```

## 🔊 Robustezza Audio — Dispositivo di Uscita

---

### [GR5] Ripristino dispositivo audio all'avvio dell'applicazione

**File modificato**: `src/renderer/src/App.tsx`

**Problema**:
`useSettingsStore` usa il middleware `persist` di Zustand per salvare `outputDeviceId`
in `localStorage`. Quando l'utente seleziona una scheda audio esterna
(es. Rødecaster Pro, Focusrite Scarlett) in Impostazioni, la preferenza viene
correttamente salvata — ma **non veniva mai applicata** al riavvio successivo.

Ogni nuova sessione ripartiva con il device di sistema di default, costringendo
l'operatore a riaprire le Impostazioni e riselezionare il device manualmente
prima di ogni trasmissione.

**Soluzione**:
Aggiunto `useEffect` in `App.tsx` che al mount dell'applicazione:

1. Legge `outputDeviceId` persisto dallo `useSettingsStore`
2. Se non è `'default'`, chiama `useAudioStore.getState().updateOutputDevice(id)`
   che a sua volta chiama `player.setOutputDevice(id)` su tutti i player attivi

```typescript
useEffect(() => {
    const { outputDeviceId } = useSettingsStore.getState();
    if (outputDeviceId && outputDeviceId !== 'default') {
        useAudioStore.getState().updateOutputDevice(outputDeviceId);
    }
    // ... listener GR3
}, []);
```

Nota: al momento del mount non ci sono ancora player attivi (nessuna clip in play),
quindi `updateOutputDevice` agisce come "predisposizione" per i player futuri.
Il costruttore di `StreamPlayer` legge già `outputDeviceId` dallo store, quindi
ogni nuova clip avviata userà già il device corretto.

---

### [GR3] Rilevamento e fallback automatico alla disconnessione dispositivo audio

**File modificati**:
- `src/renderer/src/App.tsx` — listener `ondevicechange`
- `src/renderer/src/engine/StreamPlayer.ts` — fallback in `setOutputDevice`

**Problema**:
Se durante una trasmissione la scheda audio USB viene accidentalmente scollegata
(cavo fisico, reset USB, aggiornamento driver), `setSinkId()` falliva silenziosamente
con un solo `console.warn()`. L'audio si interrompeva senza nessuna notifica visibile
all'operatore nel pannello dell'applicazione.

**Soluzione — livello App (GR3 primario)**:

Aggiunto listener `navigator.mediaDevices.addEventListener('devicechange', ...)` nel
`useEffect` di inizializzazione. Quando il browser rileva un cambio nell'elenco dei
device (connessione o disconnessione):

1. Recupera l'elenco aggiornato dei device via `enumerateDevices()`
2. Verifica se l'`outputDeviceId` corrente è ancora presente
3. Se il device è scomparso:
   - Aggiorna lo store a `'default'` (persistendo la modifica)
   - Chiama `updateOutputDevice('default')` su tutti i player attivi
   - Scrive un messaggio `⚠️` nel pannello di log debug (Ctrl+Shift+D)

Il listener viene rimosso nel cleanup del `useEffect` per evitare memory leak.

**Soluzione — livello Player (GR3 secondario)**:

In `StreamPlayer.setOutputDevice()`, il `.catch()` ora:

1. Logga il messaggio di errore nel debug store (visibile nell'overlay)
2. Tenta automaticamente il fallback a `'default'` tramite un secondo `setSinkId('default')`

```typescript
this.audioElement.setSinkId(deviceId).catch((err: Error) => {
    import('../store/useDebugStore').then(({ debugLog }) => {
        debugLog(`⚠️ Device audio non disponibile … — fallback a sistema`, 'error');
    });
    if (deviceId !== 'default') {
        this.audioElement.setSinkId('default').catch(() => {});
    }
});
```

L'import dinamico di `useDebugStore` in `StreamPlayer` evita dipendenze circolari
(StreamPlayer → Store → StreamPlayer).

# Changelog v0.9.14

*Data: 2026-04-05*

## 🔧 Robustezza — Export, Autosave e File Drop

---

### [GR9] Export: deduplicazione filename per evitare sovrascrittura silente

**File modificato**: `src/main/index.ts` — handler `export-project`

**Problema**:
Durante l'export di un progetto, i file audio venivano copiati nella cartella
`audio/` usando direttamente il loro nome originale:

```typescript
const destPath = join(audioDir, fileName);
fs.copyFileSync(originalPath, destPath);  // SOVRASCRIVE senza avviso
```

Se due clip in colonne diverse avevano lo stesso filename (scenario comune:
`intro.mp3`, `sigla.mp3`, `stacco.mp3` su drive diversi), il secondo file
sovrascriveva silenziosamente il primo. Nel file `.lmp` esportato entrambe
le clip puntavano allo stesso file audio — quello della seconda clip — corrompendo
irreversibilmente il progetto esportato.

**Soluzione**:
Prima della copia, il codice ora verifica se il file di destinazione esiste già.
In caso positivo, viene aggiunto un suffisso numerico incrementale al nome base:

```typescript
const ext = fileName.includes('.') ? fileName.split('.').pop()! : '';
const base = ext ? fileName.slice(0, -(ext.length + 1)) : fileName;
let destFileName = fileName;
let counter = 1;
while (fs.existsSync(join(audioDir, destFileName))) {
    destFileName = `${base}_${counter++}.${ext}`;
}
```

Esempio: due clip chiamate `intro.mp3` diventano `intro.mp3` e `intro_1.mp3`.
Il path nel `.lmp` esportato viene aggiornato al nome deduplicato.

---

### [GR10] Autosave con rotazione — massimo 10 file mantenuti

**File modificato**: `src/main/index.ts` — handler `save-project-silent`

**Problema**:
Il sistema di autosave creava un file con timestamp ad ogni salvataggio automatico
(ogni 5 minuti), senza mai eliminare quelli vecchi. Dopo una settimana di uso
quotidiano (8h/giorno, ogni 5 min) si accumulavano circa **672 file** nella
cartella `autosaves/` in `userData`. Nessun limite, nessuna pulizia.

**Soluzione**:
Dopo ogni salvataggio autosave, il codice ora:

1. Legge tutti i file `autosave_*.lmp` nella cartella
2. Li ordina per data di modifica (più recenti prima)
3. Elimina tutti quelli che eccedono i 10 più recenti

```typescript
const MAX_AUTOSAVES = 10;
const toDelete = allFiles.slice(MAX_AUTOSAVES);
toDelete.forEach(f => {
    try { fs.unlinkSync(join(autosaveDir, f.name)); } catch { /* ignora */ }
});
```

Il `try/catch` interno garantisce che un errore di pulizia (file bloccato,
permessi) non comprometta il salvataggio principale.

Nota: la rotazione si attiva solo per gli autosave senza filePath (nuovi progetti
non ancora salvati). I progetti già su disco usano il sistema `.bak` separato.

---

### [GR12] Validazione estensioni file in drag & drop

**File modificato**: `src/renderer/src/components/layout/MainGrid.tsx` — `handleNativeDrop`

**Problema**:
Il handler del drag & drop nativo accettava qualsiasi file droppato sulla griglia
senza nessun controllo sul tipo. Un'immagine, un PDF, un eseguibile o un video
venivano aggiunti come clip e il sistema tentava di caricarli nell'audio graph,
fallendo in modo silenzioso o generando errori criptici nel pannello debug.

**Soluzione**:
Aggiunto filtro per estensione prima di processare i file droppati:

```typescript
const SUPPORTED_AUDIO_EXTENSIONS = ['mp3', 'wav', 'ogg', 'm4a', 'aac', 'flac', 'opus', 'wma'];
const files = Array.from(e.dataTransfer.files).filter(file => {
    const ext = file.name.split('.').pop()?.toLowerCase();
    return ext && SUPPORTED_AUDIO_EXTENSIONS.includes(ext);
});
```

I file non supportati vengono silenziosamente ignorati (nessun messaggio di errore
fuorviante). La lista include tutti i formati decodificabili da Chromium/Web Audio API.

**Formati supportati**: MP3, WAV, OGG, M4A, AAC, FLAC, OPUS, WMA.

## 🔐 Sicurezza — Hardening Completo del Processo Electron

Questa release risolve il blocco di sicurezza più importante del progetto.
Quattro criticità strettamente interdipendenti vengono risolte in ordine:
**G6 → G1 → GR6 → M7**.

---

### [G6] Migrazione `file:///` → `media://` in pathUtils.ts

**File modificato**: `src/renderer/src/utils/pathUtils.ts`

**Problema**:
La funzione `toFileUrl()` generava URL con il protocollo `file:///`. L'accesso diretto
ai file locali tramite `file:///` è possibile **solo** con `webSecurity: false` attivo,
perché il browser integrato Chromium blocca le richieste cross-origin ai file locali
quando la sicurezza è attiva.

Il commento nel codice originale lo ammetteva esplicitamente:
`// 2. Native File Access (requires webSecurity: false in Main)`

Il protocollo `media://` era già completamente implementato nel main process con:
- Supporto streaming (chunking 64KB)
- Range Request native (per seeking accurato)
- Decodifica URI robusta (spazi `%20`, accenti)
- Gestione errori con status 404/500

Ma non veniva mai usato dal player principale.

**Soluzione**:
`toFileUrl()` ora genera URL `media://` con encoding corretto dei segmenti di path:
```typescript
// Drive letter (es. "C:") non viene encodato
// Ogni segmento del path viene encodato con encodeURIComponent
return `media://${encoded}`;
```

---

### [G1] `webSecurity: true` — Sicurezza Chromium finalmente attiva

**File modificato**: `src/main/index.ts` — `webPreferences`

**Problema**:
`webSecurity: false` disabilitava completamente:
- Content Security Policy (CSP) di Chromium
- Controlli CORS tra origini
- Isolamento delle origini (`origin isolation`)

Un bug XSS nel renderer o un file HTML malevolo droppato nell'app avrebbe potuto
leggere file arbitrari dal filesystem senza restrizioni.

**Soluzione**:
```typescript
webSecurity: true  // era: false
```

Reso possibile dalla migrazione G6. L'audio ora viene servito da un protocollo
sicuro e controllato (`media://`) invece che tramite accesso diretto al filesystem.

---

### [GR6] CSP Header — Content Security Policy esplicita

**File modificato**: `src/main/index.ts` — dopo `setWindowOpenHandler`

**Problema**:
Nessun header `Content-Security-Policy` veniva impostato. Il renderer poteva
eseguire script inline, caricare risorse da origini esterne e fare richieste
non autorizzate.

**Soluzione**:
Aggiunto `onHeadersReceived` che inietta la CSP su tutte le risposte:

```
default-src 'self';
media-src 'self' media:;
script-src 'self';
style-src 'self' 'unsafe-inline';
font-src 'self' data:;
img-src 'self' data:;
```

Note di design:
- `media: media:` permette il caricamento audio tramite il protocollo custom.
- `style-src 'unsafe-inline'` è temporaneamente necessario per il CSS-in-JS
  (Tailwind purge + styled components). Può essere rimosso in futuro con nonce.
- `data:` su font/img permette icone SVG inline e font base64.

---

### [M7] Rimosso `bypassCSP: true` dal protocollo `media://`

**File modificato**: `src/main/index.ts` — `registerSchemesAsPrivileged`

**Problema**:
Il flag `bypassCSP: true` sulla registrazione del protocollo `media://` istruiva
Chromium a ignorare qualsiasi Content Security Policy per le risorse caricate
tramite quel protocollo. Rendeva la CSP aggiunta in GR6 parzialmente inefficace.

**Soluzione**:
```typescript
// Prima:
{ scheme: 'media', privileges: { secure: true, supportFetchAPI: true, bypassCSP: true, stream: true } }

// Dopo:
{ scheme: 'media', privileges: { secure: true, supportFetchAPI: true, stream: true } }
```

Il flag `secure: true` è sufficiente: assegna al protocollo `media://` lo stesso
livello di attendibilità di HTTPS, consentendo fetch API, Web Audio API e streaming
senza necessità di bypass CSP.

### [Hotfix 1] Audio 404 su tutti i file — Bug URL drive letter Windows

**File modificato**: `src/renderer/src/utils/pathUtils.ts`

**Sintomo**:
```
JINGLE%206ALEX.mp3:1 Failed to load resource: the server responded with a status of 404
StreamPlayer: Error — Failed to load: K:\19 - JINGLE\JINGLE STANDARD\JINGLE 6ALEX.mp3
```
Nessun file audio veniva caricato. Il pannello debug mostrava errori 404 su ogni clip.

**Causa**:
La funzione `toFileUrl()` generava URL con **doppio slash** (`media://K:/path`).
Nella struttura di un URL standard, ciò che segue `//` è l'*authority* (hostname).
Chromium interpretava quindi `K:` come il nome host dell'URL — un hostname non valido
contenente `:`. Il risultato era che la lettera di drive veniva persa e il path
rimanente (`/19 - JINGLE/...`) non corrispondeva ad alcun file nel filesystem.

**Fix**:
Sostituito `media://` con `media:///` (**triplo slash**):

```typescript
// Prima (errato): drive letter trattata come hostname
return `media://${encoded}`;   // → media://K:/path/file.mp3

// Dopo (corretto): authority vuota, drive letter nel path
return `media:///${encoded}`;  // → media:///K:/path/file.mp3
```

Con il triplo slash:
- Authority = vuota (nessun hostname)
- Path = `/K:/path/file.mp3`
- Il handler nel main process riceve `/K:/path`, rimuove il leading `/`, ottiene `K:/path`

Identico al funzionamento di `file:///C:/path` che Chromium gestisce nativamente.

**Verificato** ✅ — tutti i file (MP3, WAV) su drive C:, J:, K: si riproducono correttamente.

---

### [Hotfix 2] Tre errori CSP che bloccavano script, audio e update check

**File modificato**: `src/main/index.ts` — CSP in `onHeadersReceived`

**Sintomi**:
```
Refused to execute inline script — violates "script-src 'self'"
Refused to connect to 'https://www.runtimeradio.it/versions.json' — "default-src 'self'"
```

**Causa 1 — script-src troppo restrittiva**:
Vite genera nell'`index.html` un tag `<script type="module">` inline per
l'inizializzazione del bundle. La direttiva `script-src 'self'` senza
`'unsafe-inline'` bloccava questo script, impedendo il caricamento dell'app.

# Changelog v0.9.11

*Data: 2026-04-05*

## 🔴 Correzioni Critiche — Stabilità Engine Audio

### [G2] Memory leak: nodi Web Audio API mai disconnessi

**File modificato**: `src/renderer/src/engine/StreamPlayer.ts` — metodo `cleanup()`

**Problema**:
Ogni istanza di `StreamPlayer` crea nel costruttore due nodi Web Audio:

- `sourceNode` (`MediaElementAudioSourceNode`) — collega il tag `<audio>` all'audio graph
- `volumeGainNode` (`GainNode`) — controlla il volume della clip

Quando una clip veniva sostituita o fermata, `stopClip` chiamava `player.cleanup()`,
che disconnetteva correttamente `volumeGainNode` ma **non faceva nulla su `sourceNode`**.

Il nodo `MediaElementAudioSourceNode` rimaneva agganciato all'audio graph come **nodo
zombie**: ancora vivo, ancora allocato, impossibile da raccogliere dal GC perché
il `BaseAudioContext` mantiene un riferimento interno a tutti i nodi connessi.

In una sessione broadcast di 8 ore con decine di switch di clip, l'audio graph cresceva
indefinitamente, causando:
- Degrado progressivo delle performance del renderer
- Aumento costante del consumo di memoria
- Potenziale crash del processo Electron dopo ore di uso continuativo

**Soluzione**:
In `cleanup()`, aggiunto il blocco mancante:

```typescript
if (this.sourceNode) {
    this.sourceNode.disconnect();
    this.sourceNode = null;  // Permette al GC di raccogliere l'oggetto
}
```

`sourceNode` viene anche azzerato a `null` dopo la disconnessione, così il GC può
liberare la memoria occupata dal nodo.

---

### [G3] Race condition: clip loading asincrono senza cancellazione

**File modificato**: `src/renderer/src\store\useAudioStore.ts` — funzione `playClip`

**Problema**:
`playClip` è una funzione `async` che esegue `await player.load(freshClip.path)` prima
di avviare la riproduzione. Se l'operatore swicchia clip rapidamente (scenario tipico
in broadcast live), possono accadere due operazioni concorrenti:

1. `playClip("clip-A")` avvia il load → `await player.load("clip-A.mp3")`
2. Prima che il load finisca, `playClip("clip-B")` viene chiamata

Quando il load di "clip-A" si risolve (anche 0.5–2 secondi dopo), il codice continuava
a chiamare `player.play()` **senza sapere che nel frattempo era già stata avviata
"clip-B"**. Risultato: due clip che partono simultaneamente, stato del store non
allineato con la riproduzione effettiva.

**Soluzione — Generation ID**:
Aggiunta una `Map<string, number>` (module-level, fuori dallo store) che tiene traccia
di un contatore incrementale per ogni `clipId`:

```typescript
const playGenerations = new Map<string, number>();
```

All'inizio di ogni `playClip`, il contatore della clip viene incrementato e salvato
nella variabile locale `generation`. Dopo l'`await load()`, si confronta il contatore
salvato con quello corrente nella Map:

```typescript
const generation = (playGenerations.get(freshClip.id) || 0) + 1;
playGenerations.set(freshClip.id, generation);
// ... await player.load() ...
if ((playGenerations.get(freshClip.id) || 0) !== generation) {
    player.cleanup();  // load obsoleto, scartare
    return;
}
player.play();
```

Se il contatore è cambiato (perché una chiamata più recente ha già preso il controllo),
l'operazione obsoleta viene scartata e il player creato viene immediatamente pulito
(evitando anche un secondo memory leak).

Il log di debug riporta il motivo dello scarto: `Load obsoleto scartato per [nome] (gen N)`.

# Changelog v0.9.10

*Data: 2026-04-05*

## 🔴 Correzioni Critiche — Engine Audio

### [G4] Stacco (jingle): i volumi soppressi non venivano ripristinati alla fine

**File modificato**: `src/renderer/src/store/useAudioStore.ts` — funzione `stopClip`

**Problema**:
Quando uno stacco terminava natura (o veniva fermato manualmente), la funzione `stopClip`
rimuoveva la clip dall'elenco degli attivi e chiamava `evaluateMix` — il che è corretto.
Tuttavia il dizionario `suppressedClips` (che traccia le clip sileniate dallo stacco)
**non veniva mai svuotato** in `stopClip`. Il dict cresceva indefinitamente e non veniva
mai usato da `evaluateMix` (che ricalcola tutto da zero), diventando di fatto
stato fantasma che occupava memoria.

Problema correlato: senza pulizia di `suppressedClips`, future ottimizzazioni che
consultassero quel dict avrebbero trovato dati stantii, portando a ripristino errato.

**Soluzione**:
In `stopClip`, dopo la rimozione della clip da `activeClips`:
- Se la clip era uno **stacco** (`behavior === 'stacco'`): `suppressedClips` viene
  azzerato completamente. `evaluateMix`, ricalcolando lo stato senza lo stacco attivo,
  ripristina automaticamente i volumi via `fadeTo()` su tutte le clip ancora attive.
- Se era una **clip normale che era soppressa**: la sua entry viene rimossa dal dict,
  le altre restano.

Scenario ripristinato correttamente: stacco suona → musica sottostante riprende volume
pieno alla fine del jingle senza intervento manuale.

---

### [G7] Stale closure nei callback asincroni: `currentStore` → `get()`

**File modificato**: `src/renderer/src/store/useAudioStore.ts` — funzione `playClip`

**Problema**:
La variabile `currentStore = get()` viene catturata all'inizio di `playClip` e poi
usata in due closure asincrone:

1. `player.onEnded(() => { currentStore.stopClip(freshClip.id); ... })`
2. `preShowClips.forEach(ac => currentStore.stopClip(ac.clip.id))`

`currentStore` è un **snapshot dello store Zustand al momento della chiamata**, non
un riferimento live. Sebbene Zustand renda le action functions stabili, l'uso di
`currentStore` invece di `get()` rompe la leggibilità del pattern e, in certe
condizioni di race condition (es. store parzialmente ricostruito durante hot-reload
in Electron), può portare a chiamate su un'istanza non più valida.

Più important: il pattern `currentStore.stopClip()` è semanticame ingannevole — lascia
intendere che si chiami su uno stato catturato (stale), quando invece si vuole sempre
agire sullo stato corrente.

**Soluzione**:
Sostituito `currentStore.stopClip(...)` con `get().stopClip(...)` in entrambi i punti,
rendendo esplicita l'intenzione di ottenere sempre lo stato fresco.

## 🟠 Correzioni Gravi — Performance

### [G8] `setInterval` Zustand incondizionato: 10 set()/s inutili

**File modificato**: `src/renderer/src/store/useAudioStore.ts` — factory dello store

**Problema**:
Alla creazione dello store Zustand, viene avviato un `setInterval(fn, 100)` che chiama
`_syncProgress()` ogni 100ms. `_syncProgress()` chiama `set()` sullo store, causando
una rivalutazione Zustand e il re-render di **tutti i componenti subscriber**
— inclusi ClipCard, VUMeter, GlobalControls — ogni 100ms, **anche quando nessuna
clip è in riproduzione**.

In una sessione di 8 ore: ~288.000 `set()` inutili, con tutti i re-render annessi.
Questo si manifesta come consumo CPU residuo anche con l'applicazione ferma.

**Soluzione**:
Aggiunto guard condizionato prima della chiamata a `_syncProgress()`:

```typescript
setInterval(() => {
    if (Object.keys(get().activeClips).length > 0) {
        get()._syncProgress();
    }
}, 100);
```

Quando non ci sono clip attive, il set() Zustand non viene mai chiamato → zero re-render
inutili. Il polling rimane a 100ms per garantire fluidità delle progress bar durante
la riproduzione.

**Nota Desktop**: questa ottimizzazione è particolarmente rilevante per un'app desktop
live che può rimanere aperta per ore durante una trasmissione, a differenza di una
web app che viene riaperta frequentemente.
