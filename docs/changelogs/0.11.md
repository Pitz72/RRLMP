# Changelog v0.11.2 (2026-04-06)

## 🚑 HOTFIX DEFINITIVO: FFprobe e ASAR Unpacking
Analisi forense e correzione totale dei path per la comunicazione Child Process nell'ambiente pacchettizzato.

### 🐛 Il Problema: `TypeError ASAR/Undefined`
Nonostante l'hotfix precedente avesse ripreso la compatibilità CJS nativa di Node, l'eseguibile ha provocato in Main Process l'errore d'avvio: `TypeError: Cannot read properties of undefined (reading 'path')`.
1. **ESM Interop CJS**: L'importazione ES6 `import ffprobeStatic from 'ffprobe-static'` traslata dal bundler Vite si aspettava l'oggetto sotto `default`, fallendo miseramente nell'output asar e producendo `undefined`.
2. **ASAR File System Lock**: Le estensioni statiche `.exe` racchiuse nel file `app.asar` generato da Electron-Builder non venivano estratte, rendendo vano lo `spawn()` del Child Process FFmpeg, dato che un eseguibile locale Windows non può runnare all'interno di un ghost-zip tree.

### 🛠️ La Soluzione Forense
- **Require Strict & Defensive Coding**: Inettata la funzione `require` nativa forzando il caricamento dell'Object Export (`require('ffprobe-static')`) con fallback dinamico alla proprietà effettiva per prevenire TypeErrors.
- **ASAR Unpack**: Scritte regole in `package.json` (`"asarUnpack"`) obbligando *NSIS* ad estrarre in clair-text i path `node_modules/ffmpeg-static/**/*.exe` su disco.
- **Virtual Path Hack**: Inserita la patch industriale `replace('app.asar', 'app.asar.unpacked')` che riconosce dinamicamente la nuova sandbox unpacked in produzione e previene `ENOENT`.

Ora le librerie statiche operano su vero File-System Windows!

# Changelog v0.11.1 (2026-04-06)

## 🚑 HOTFIX: Compatibilità ESM/CommonJS in App Packaged
Questo aggiornamento è un hotfix immediato per un errore fatale che si verificava unicamente nell'ambiente pacchettizzato finale (`app.asar`) per Windows.

### 🐛 Il Problema: `ERR_PACKAGE_PATH_NOT_EXPORTED`
Durante l'avvio della versione pacchettizzata v0.11.0, Node originava un fallimento irreparabile causato dal pacchetto `music-metadata`. La versione `^11.12.3` è scritta in puro ECMAScript Module (ESM) e priva del wrapper di compatibilità `module-sync/require` nel `package.json`, collidendo mortalmente con l'infrastruttura CommonJS originata dal processo Electron 28 (`node_modules/cjs/loader`).

### 🛠️ La Soluzione (Downgrade Sicuro)
L'integrità del parser `AudioProcessor` è stata ristabilita applicando un downgrade industriale di `music-metadata` verso la versione pre-ESM: `7.14.0`. 
Questo ripristina la stabilità assoluta della decodifica nativa in CJS, rendendo nuovamente compatibile The Wakeform Editor con il Main Server Packaged bypassando deficienze di bundling su Electron Builder.

*La build NSIS `.exe` è stata ri-compilata.*

# Changelog v0.11.0 (2026-04-06)

## 🎉 RELASE UFFICIALE: ARCHITETTURA "MAIN-SIDE-HEAVY"
Questo rilascio segna la fine del refactoring strutturale per risolvere i fatali `0xC0000005 Access Violation`. RRLMP non si basa più sulle Web Audio API di Chromium per generare le rappresentazioni audio di base su file giganti, ma fa affidamento su veri binari industriali (`FFmpeg` e `music-metadata`).

### 📝 Resoconto del Progresso
Sintesi dell'avanzamento dalle versioni intermedie:

#### `v0.10.5`
- Creazione motore indipendente Node.js (`AudioProcessor`) con `music-metadata`.
- Estrazione dinamica della forma d'onda asincrona via Node Stream e FFmpeg per bypassare le restrizioni della sandbox.

#### `v0.10.6`
- Integrazione Layer IPC via `preload/index.ts` chiuso e typed, garantendo transizioni dei dati asincroni JSON/Buffer trasparenti e memory-safe verso il React Frontend.

#### `v0.10.7`
- Riabilitazione visuale del `WaveformEditor`. La UI reagisce reattivamente assecondando lo stream di calcolo di backend e renderizza array minimizzati senza saturare RAM, offrendo una UX pulita e reattiva con indicatori di stato.

#### `v0.10.8`
- Rifattorizzazione robusta di `media://` IPC intercept, portando l'allocazione base (`HighWaterMark`) a un range industriale di `1MB`, stroncando fenomeni di instabilità da disk-spinning o interruzioni di decodifica durante seeking accelerato.

### 🛡️ Conclusioni sulla Stabilità
La piattaforma Electron è ora consolidata come un cruscotto UI, lasciando il calcolo grezzo a processi esterni. L'obiettivo architettonico fissato a roadmap è stato raggiunto.

### 🛠️ Processo di Build e TypeScript Fixes
Durante la pacchettizzazione finale (NSIS/Electron Builder), sono stati riscontrati e corretti errori bloccanti del compilatore TypeScript (`TS1259`, `TS6133`, `TS7006`) introdotti in fase sperimentale in `AudioProcessor.ts`.
- Sostituito l'import default incompatibile per ESModule (`import ffmpeg from 'fluent-ffmpeg'`) con il binding astratto `import * as ffmpeg`.
- Rimosse variabili non referenziate (`Transform`, `spawn`, `WaveformData`) per rispettare le policy rigide di TypeScript nel processo Main.
- Tipizzati esplicitamente come `any` o `Buffer` i callback nei listeners di `FFmpeg` (`on('error')` e `on('data')`) per chiudere colli di bottiglia della pipeline di check del compilatore.
La build `v0.11.0` (eseguibile Windows `.exe`) è stata generata correttamente.
