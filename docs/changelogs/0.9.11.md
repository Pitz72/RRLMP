# Changelog v0.9.11

*Data: 2026-04-05*

## 🔴 Correzioni Critiche — Stabilità Engine Audio

### [G2] Memory leak: nodi Web Audio API mai disconnessi

**File modificato**: `src/renderer/src/engine/StreamPlayer.ts` — metodo `cleanup()`

**Problema**:
Ogni istanza di `StreamPlayer` crea nel costruttore due nodi Web Audio:

- `sourceNode` (`MediaElementAudioSourceNode`) — collega il tag `<audio>` all'audio graph
- `volumeGainNode` (`GainNode`) — controlla il volume della clip

Quando una clip veniva sostituita o fermata, `stopClip` chiamava `player.cleanup()`,
che disconnetteva correttamente `volumeGainNode` ma **non faceva nulla su `sourceNode`**.

Il nodo `MediaElementAudioSourceNode` rimaneva agganciato all'audio graph come **nodo
zombie**: ancora vivo, ancora allocato, impossibile da raccogliere dal GC perché
il `BaseAudioContext` mantiene un riferimento interno a tutti i nodi connessi.

In una sessione broadcast di 8 ore con decine di switch di clip, l'audio graph cresceva
indefinitamente, causando:
- Degrado progressivo delle performance del renderer
- Aumento costante del consumo di memoria
- Potenziale crash del processo Electron dopo ore di uso continuativo

**Soluzione**:
In `cleanup()`, aggiunto il blocco mancante:

```typescript
if (this.sourceNode) {
    this.sourceNode.disconnect();
    this.sourceNode = null;  // Permette al GC di raccogliere l'oggetto
}
```

`sourceNode` viene anche azzerato a `null` dopo la disconnessione, così il GC può
liberare la memoria occupata dal nodo.

### [G3] Race condition: clip loading asincrono senza cancellazione

**File modificato**: `src/renderer/src\store\useAudioStore.ts` — funzione `playClip`

**Problema**:
`playClip` è una funzione `async` che esegue `await player.load(freshClip.path)` prima
di avviare la riproduzione. Se l'operatore swicchia clip rapidamente (scenario tipico
in broadcast live), possono accadere due operazioni concorrenti:

1. `playClip("clip-A")` avvia il load → `await player.load("clip-A.mp3")`
2. Prima che il load finisca, `playClip("clip-B")` viene chiamata

Quando il load di "clip-A" si risolve (anche 0.5–2 secondi dopo), il codice continuava
a chiamare `player.play()` **senza sapere che nel frattempo era già stata avviata
"clip-B"**. Risultato: due clip che partono simultaneamente, stato del store non
allineato con la riproduzione effettiva.

**Soluzione — Generation ID**:
Aggiunta una `Map<string, number>` (module-level, fuori dallo store) che tiene traccia
di un contatore incrementale per ogni `clipId`:

```typescript
const playGenerations = new Map<string, number>();
```

All'inizio di ogni `playClip`, il contatore della clip viene incrementato e salvato
nella variabile locale `generation`. Dopo l'`await load()`, si confronta il contatore
salvato con quello corrente nella Map:

```typescript
const generation = (playGenerations.get(freshClip.id) || 0) + 1;
playGenerations.set(freshClip.id, generation);
// ... await player.load() ...
if ((playGenerations.get(freshClip.id) || 0) !== generation) {
    player.cleanup();  // load obsoleto, scartare
    return;
}
player.play();
```

Se il contatore è cambiato (perché una chiamata più recente ha già preso il controllo),
l'operazione obsoleta viene scartata e il player creato viene immediatamente pulito
(evitando anche un secondo memory leak).

Il log di debug riporta il motivo dello scarto: `Load obsoleto scartato per [nome] (gen N)`.
