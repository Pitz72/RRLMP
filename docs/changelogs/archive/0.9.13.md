# Changelog v0.9.13

*Data: 2026-04-05*

## 🔐 Sicurezza — Hardening Completo del Processo Electron

Questa release risolve il blocco di sicurezza più importante del progetto.
Quattro criticità strettamente interdipendenti vengono risolte in ordine:
**G6 → G1 → GR6 → M7**.

---

### [G6] Migrazione `file:///` → `media://` in pathUtils.ts

**File modificato**: `src/renderer/src/utils/pathUtils.ts`

**Problema**:
La funzione `toFileUrl()` generava URL con il protocollo `file:///`. L'accesso diretto
ai file locali tramite `file:///` è possibile **solo** con `webSecurity: false` attivo,
perché il browser integrato Chromium blocca le richieste cross-origin ai file locali
quando la sicurezza è attiva.

Il commento nel codice originale lo ammetteva esplicitamente:
`// 2. Native File Access (requires webSecurity: false in Main)`

Il protocollo `media://` era già completamente implementato nel main process con:
- Supporto streaming (chunking 64KB)
- Range Request native (per seeking accurato)
- Decodifica URI robusta (spazi `%20`, accenti)
- Gestione errori con status 404/500

Ma non veniva mai usato dal player principale.

**Soluzione**:
`toFileUrl()` ora genera URL `media://` con encoding corretto dei segmenti di path:
```typescript
// Drive letter (es. "C:") non viene encodato
// Ogni segmento del path viene encodato con encodeURIComponent
return `media://${encoded}`;
```

---

### [G1] `webSecurity: true` — Sicurezza Chromium finalmente attiva

**File modificato**: `src/main/index.ts` — `webPreferences`

**Problema**:
`webSecurity: false` disabilitava completamente:
- Content Security Policy (CSP) di Chromium
- Controlli CORS tra origini
- Isolamento delle origini (`origin isolation`)

Un bug XSS nel renderer o un file HTML malevolo droppato nell'app avrebbe potuto
leggere file arbitrari dal filesystem senza restrizioni.

**Soluzione**:
```typescript
webSecurity: true  // era: false
```

Reso possibile dalla migrazione G6. L'audio ora viene servito da un protocollo
sicuro e controllato (`media://`) invece che tramite accesso diretto al filesystem.

---

### [GR6] CSP Header — Content Security Policy esplicita

**File modificato**: `src/main/index.ts` — dopo `setWindowOpenHandler`

**Problema**:
Nessun header `Content-Security-Policy` veniva impostato. Il renderer poteva
eseguire script inline, caricare risorse da origini esterne e fare richieste
non autorizzate.

**Soluzione**:
Aggiunto `onHeadersReceived` che inietta la CSP su tutte le risposte:

```
default-src 'self';
media-src 'self' media:;
script-src 'self';
style-src 'self' 'unsafe-inline';
font-src 'self' data:;
img-src 'self' data:;
```

Note di design:
- `media: media:` permette il caricamento audio tramite il protocollo custom.
- `style-src 'unsafe-inline'` è temporaneamente necessario per il CSS-in-JS
  (Tailwind purge + styled components). Può essere rimosso in futuro con nonce.
- `data:` su font/img permette icone SVG inline e font base64.

---

### [M7] Rimosso `bypassCSP: true` dal protocollo `media://`

**File modificato**: `src/main/index.ts` — `registerSchemesAsPrivileged`

**Problema**:
Il flag `bypassCSP: true` sulla registrazione del protocollo `media://` istruiva
Chromium a ignorare qualsiasi Content Security Policy per le risorse caricate
tramite quel protocollo. Rendeva la CSP aggiunta in GR6 parzialmente inefficace.

**Soluzione**:
```typescript
// Prima:
{ scheme: 'media', privileges: { secure: true, supportFetchAPI: true, bypassCSP: true, stream: true } }

// Dopo:
{ scheme: 'media', privileges: { secure: true, supportFetchAPI: true, stream: true } }
```

Il flag `secure: true` è sufficiente: assegna al protocollo `media://` lo stesso
livello di attendibilità di HTTPS, consentendo fetch API, Web Audio API e streaming
senza necessità di bypass CSP.

## ⚠️ Note di Testing

Questa release cambia radicalmente il modo in cui i file audio vengono caricati.
**Testare obbligatoriamente**:

1. **Riproduzione base**: play/stop di clip MP3, WAV, OGG, FLAC
2. **Seeking**: trascinamento della progress bar
3. **Trim**: clip con trimStart/trimEnd configurati
4. **Fade**: clip con fadeIn/fadeOut
5. **Path con spazi e caratteri speciali**: es. `C:\Musica\Artista & Band\traccia (live).mp3`
6. **Path con accenti**: es. `C:\Archivio\Musica Français\chanson.mp3`

Se un formato specifico non si carica, il log debug mostrerà l'errore nel
pannello diagnostico (`StreamPlayer: Error ...`).

## 🛠️ Hotfix Post-Release — Test su progetto reale (2026-04-05)

Dopo la build iniziale di 0.9.13, il test su un progetto esistente ha rivelato
due errori bloccanti, entrambi risolti nella stessa versione (rebuild).

---

### [Hotfix 1] Audio 404 su tutti i file — Bug URL drive letter Windows

**File modificato**: `src/renderer/src/utils/pathUtils.ts`

**Sintomo**:
```
JINGLE%206ALEX.mp3:1 Failed to load resource: the server responded with a status of 404
StreamPlayer: Error — Failed to load: K:\19 - JINGLE\JINGLE STANDARD\JINGLE 6ALEX.mp3
```
Nessun file audio veniva caricato. Il pannello debug mostrava errori 404 su ogni clip.

**Causa**:
La funzione `toFileUrl()` generava URL con **doppio slash** (`media://K:/path`).
Nella struttura di un URL standard, ciò che segue `//` è l'*authority* (hostname).
Chromium interpretava quindi `K:` come il nome host dell'URL — un hostname non valido
contenente `:`. Il risultato era che la lettera di drive veniva persa e il path
rimanente (`/19 - JINGLE/...`) non corrispondeva ad alcun file nel filesystem.

**Fix**:
Sostituito `media://` con `media:///` (**triplo slash**):

```typescript
// Prima (errato): drive letter trattata come hostname
return `media://${encoded}`;   // → media://K:/path/file.mp3

// Dopo (corretto): authority vuota, drive letter nel path
return `media:///${encoded}`;  // → media:///K:/path/file.mp3
```

Con il triplo slash:
- Authority = vuota (nessun hostname)
- Path = `/K:/path/file.mp3`
- Il handler nel main process riceve `/K:/path`, rimuove il leading `/`, ottiene `K:/path`

Identico al funzionamento di `file:///C:/path` che Chromium gestisce nativamente.

**Verificato** ✅ — tutti i file (MP3, WAV) su drive C:, J:, K: si riproducono correttamente.

---

### [Hotfix 2] Tre errori CSP che bloccavano script, audio e update check

**File modificato**: `src/main/index.ts` — CSP in `onHeadersReceived`

**Sintomi**:
```
Refused to execute inline script — violates "script-src 'self'"
Refused to connect to 'https://www.runtimeradio.it/versions.json' — "default-src 'self'"
```

**Causa 1 — script-src troppo restrittiva**:
Vite genera nell'`index.html` un tag `<script type="module">` inline per
l'inizializzazione del bundle. La direttiva `script-src 'self'` senza
`'unsafe-inline'` bloccava questo script, impedendo il caricamento dell'app.

**Fix**: aggiunto `'unsafe-inline'` a `script-src`.

**Causa 2 — connect-src mancante**:
Il check aggiornamenti chiama `https://www.runtimeradio.it/versions.json`.
Non essendo `connect-src` specificata, veniva applicato il fallback `default-src 'self'`
che blocca qualsiasi richiesta verso origini esterne.

**Fix**: aggiunta direttiva `connect-src 'self' https://www.runtimeradio.it`.

**CSP finale applicata**:
```
default-src 'self';
media-src 'self' media:;
script-src 'self' 'unsafe-inline';
style-src 'self' 'unsafe-inline';
font-src 'self' data:;
img-src 'self' data:;
connect-src 'self' https://www.runtimeradio.it;
```

**Verificato** ✅ — app si avvia, audio funziona, update check non genera più errori.
